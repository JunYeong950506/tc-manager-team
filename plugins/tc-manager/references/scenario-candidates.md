# 시나리오 후보 도출과 복수 선택

create는 티켓당 TC 1개를 만들거나 티켓 수에 맞춰 종료하는 업무가 아니다. 티켓은 근거 단위이고 TC는 독립적으로 수행·판정할 수 있는 시나리오 단위다. 한 티켓에서 여러 후보가 나올 수 있으며 여러 티켓의 공통 동작은 하나의 후보와 연결할 수 있다. 필요한 개수는 검증 범위로 결정하고 티켓별 최소/최대 개수나 고정 할당량을 두지 않는다.

## 후보 도출

1. 선택한 작성 관점과 직접 입력을 기준으로 실제 조회한 요구사항·AC를 검증 가능한 동작/상태/조건으로 나눈다. Jira 연결 문서가 없다는 이유로 Confluence 탐색을 생략하지 않는다. workflow.md의 검색 절차와 접근 실패 구분을 따른다.
2. 각 요구사항에 관련된 다음 축을 대조한다. 기본값은 정상·예외·경계·권한·상태 전이, 성능은 최초/반복 동작·데이터/대상 규모·동시 작업·응답/처리량/자원 관찰, 안정성은 반복·장시간·중단/실패/복구·작업 중 전환·상태 동기화를 검토한다. 선택하지 않은 관점은 자동 추가하지 않는다. 모든 축을 기계적으로 곱하지 않고 다른 결함을 드러낼 의미 있는 조합을 후보로 만든다.
3. 서로 다른 준비 상태·자극·관찰 결과로 독립적인 실패를 판정할 수 있으면 별도 후보로 나눈다. 하나의 TC에 여러 독립 시나리오를 긴 스텝으로 몰아 넣거나 문장·수치만 바꿔 개수를 늘리지 않는다. 같은 목적·조건·입력·기대 결과는 통합하고 관련 티켓과 관점은 모두 보존한다.
4. 각 후보에 실제 출처와 기대 동작의 근거를 연결한다. 시험 방법으로 제안한 조합은 제안이라고 표시한다. 미지원 기능·확인하지 않은 카메라 수·시간 제한·허용 오차를 제품 기준으로 만들지 않는다. 필요한 기준이 미확인이면 needs_evidence 후보로 남겨 선택 전에 표시한다. '즉시', '영향 없음' 같은 표현을 근거 없는 정량 합격 기준으로 바꾸지 않는다.
5. `library.md`에 따라 기존 TC와 후보끼리 내용 중복을 대조한다. 제목 스캔이나 이슈 링크 0건은 후보 검색 결과일 뿐 중복 없음의 증거가 아니다. 유사 TC는 목적·Precondition·Script·환경까지 읽고 reuse/revise/new/exclude와 이유를 기록한다. DB/본문 조회가 불가능하면 duplicate_check=unavailable/partial로 표시하고 신규 필요성은 잠정 판단으로 남긴다.
6. 요구사항 × 선택 관점의 누락을 한 번 점검한다. 후보가 하나뿐이어도 충분한 근거가 있으면 허용하지만 '티켓별 하나 작성 완료'를 커버리지 완료로 사용하지 않는다. 관련 후보·기존 TC 재사용·범위 밖·근거 부족 중 무엇으로 처리했는지 기록한다. 전수 가능한 모든 시나리오를 발견했다고 단정하지 않는다.

## 사용자에게 보여줄 목록

상세 본문 작성 전에 전체 후보를 짧은 표로 보여준다. `후보 ID | 관련 티켓 | 시나리오/핵심 판정 | 관점 | 신규·재사용·개정 | 근거/중복 확인 제한`을 포함한다. 후보 ID는 C001처럼 안정적인 로컬 ID이며 실제 Zephyr key로 표시하지 않는다. 기존 TC 재사용/개정에는 실제 key를 함께 표시한다. 기본 추천은 제시할 수 있지만 사용자의 선택으로 간주하지 않는다.

`scenario-candidates.json`에 목록과 선택 상태를 저장한다. 최상위에는 revision, preferences, coverage, selection_status(pending/answered), selected_ids를 둔다. 각 후보에는 id, ticket_keys, title, perspectives, setup_and_trigger, expected_observation, evidence_refs, evidence_status(confirmed/needs_evidence), duplicate_check(complete/partial/unavailable), disposition(new/reuse/revise/exclude), existing_keys, reason을 보존한다. 초기 pending의 빈 selected_ids는 사용자의 '선택 안 함'과 다르다. workflow.json에는 이 파일의 경로를 연결한다.

## 선택과 후속 처리

- 부모 Claude가 `AskUserQuestion`의 `multiSelect: true`로 "작성하거나 재사용할 시나리오를 골라 주세요. 여러 개 선택할 수 있습니다."라고 묻는다. 선택지 label은 후보 ID와 짧은 제목, description은 관점·핵심 판정·신규/재사용/개정·제한이다. 직접 입력에서 ID 목록, 전체 선택, 제외 목록, 추가 시나리오도 받을 수 있다.
- 현재 도구 스키마의 선택지 제한(보통 질문당 2~4개)에 맞춰 후보를 묶어 제시하고 진행 위치를 표시한다. 후보가 많아도 처음 4개만 제시하고 나머지를 버리지 않는다. 묶음별 선택을 누적하고 이미 응답한 묶음을 반복하지 않는다. 후보가 하나면 선택/제외 질문을 사용한다. 사용자가 전체 목록에 대해 '모두' 또는 ID 목록을 명시하면 그 응답으로 선택을 확정하고 페이지 질문을 생략한다. '이 묶음 선택 안 함'이라는 명시적 응답은 빈 선택으로 저장한다.
- 도구가 없으면 동일한 전체 목록과 후보 ID로 복수 선택을 받는다. 취소·무응답은 대기 상태이며 임의 전체 선택이나 추천 선택으로 대체하지 않는다. 새 후보 추가 또는 의미 있는 변경 시 revision을 올리고 변경된 후보만 추가로 선택받는다. 그대로인 후보의 기존 선택은 유지한다.
- 선택된 new만 draft.json으로 상세 작성한다. reuse는 기존 key와 충족 범위를 제시하며 복제 생성하지 않는다. revise는 선택된 기존 TC의 개정 초안으로 구분한다. 선택된 needs_evidence는 근거 보완/미해결 표시를 이어가고 선택받았다는 이유로 합격 기준을 추측하지 않는다. 선택되지 않은 후보는 목록에 보존하되 생성하지 않는다.
- 작성 후 기존 내용 검토와 사람의 최종 검토를 유지한다. 후보 선택은 상세 본문이나 Zephyr 쓰기 승인이 아니다. 완료 보고에는 도출·선택·재사용·개정·신규·미해결 수와 남은 범위를 구분한다.
- 재개는 동일 revision의 후보·선택·원격 key를 읽어 이어간다. 기존 TC가 이미 등록된 후 추가 후보를 요청받으면 등록된 TC도 중복 대조에 포함한다. 원격 TC를 다시 만들거나 기존 것을 자동 삭제하지 않는다.
- plan 내부의 부족 TC 작성은 후보 목록을 계획에 합쳐 한 번에 선택받는다. 이미 사람이 검토한 구체적 시나리오 목록은 그 선택을 재사용한다. 단순히 기능/성능/안정성 관점을 선택한 것은 개별 후보를 모두 선택한 뜻이 아니다.
