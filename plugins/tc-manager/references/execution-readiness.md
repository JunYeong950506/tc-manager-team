# 실행 Agent에 전달할 수 있는 Test Script

작성/변환한 Script와 명시된 실행 입력을 읽고 아래를 점검한다. Objective/Precondition에만 있는 조건을 실행 Agent가 알아서 발견하리라고 가정하지 않는다. 단순한 TC에 무관한 분기·로그·복구 단계를 형식적으로 늘리지 않는다. 이 점검은 실제 제품 실행 성공이나 자동 의미 검증이 아니다.

| 점검 | 작성·보완 규칙 |
|---|---|
| 입력과 준비 상태 | 필요한 계정 역할·개별 클라이언트·시스템·대상·데이터의 별칭을 실제 실행 입력에 연결한다. 허용/제외 환경·권한·초기 상태를 첫 준비 단계나 명시적 입력 참조에서 확인한다. 미확인이면 실행 불가 원인과 증거를 남긴다. |
| 구체적인 변경 내용 | '다른 채널', '추가 또는 변경'만 남기지 않는다. 실행 전에 초기 구성 L0와 각 변경 구성 A1/B1처럼 재현 가능한 값을 선택·기록한다. 환경에 맞는 값 선택은 Agent가 수행할 수 있으며 제품 합격 기준으로 오해하지 않는다. |
| 단계 간 연결 | 후속 단계가 필요로 하는 상태를 선행 결과가 보장하는지 확인한다. 보장되지 않으면 진입 조건과 분기를 명시한다. 편집이 사라졌다면 몰래 다시 편집하지 않는다. 기존 관찰 결과를 보존하고 조건 미성립으로 후속 구간을 중단한다. 앞 단계에서 확인한 실패도 그대로 유지한다. |
| 순서와 동시성 | 편집 중 상태의 중첩과 저장 요청의 중첩은 다른 시험이다. A 저장 완료 후 B 저장이면 동시 편집 후 순차 저장으로 표현한다. 실제 동시 저장을 요구하면 동기화 방법과 요청 중첩 증거가 필요하며 없으면 동시 저장 검증으로 보고하지 않는다. |
| 관찰 구간 | 짧은 상태 변화를 유발하는 조작 전에 관련 화면/이벤트 기록을 시작한다. 관찰 시작·완료 조건·실행 대기 한도·시간 초과 후 동작을 연결한다. 대기 한도는 실행 정책에서 선택·기록하며 임의 성능 합격 기준으로 쓰지 않는다. |
| 기대 상태의 기준 | 화면끼리 같다는 것뿐 아니라 합의된 정확한 기대 구성과 각각 비교한다. '마지막 저장 우선'이면 마지막 저장 직전 실제 구성이 B1인지 보존하고 저장된 B1을 기준으로 비교한다. 어떤 구성을 저장했는지 모르면 해당 최종 상태를 Pass로 판정할 수 없다. |
| 복구 전후 분리 | 재시도·새로고침·재접속 전에 최초 관찰과 결과를 확정·보존한다. 복구 후 결과는 별도 기록하며 최초 실패를 성공으로 덮어쓰지 않는다. 원문에 복구 확인이 없으면 불필요한 새 시험을 추가하지 않는다. |
| 권한 증거의 범위 | 비활성 메뉴/버튼은 UI 진입 차단의 근거다. 실제 수정·삭제 요청의 거부까지 주장하려면 해당 안전한 조작·거부 확인 절차가 필요하다. 원문의 더 넓은 권한 검증을 조용히 UI 확인으로 축소하지 말고 미검증 범위를 표시하거나 별도 시험을 제안한다. |
| 로그와 오류 처리 | 로그가 필요한 시험이면 실행 환경의 수집 대상·방법·권한·시간 범위를 참조한다. 수집 실패는 오류 없음이 아니다. 정상 권한의 저장에서 발생한 Forbidden을 근거 없이 정상 예외로 인정하지 않는다. 기대 거부는 해당 역할·조작·출처가 연결된 경우에만 구분한다. |
| 종료와 보존 | 정상 완료·조건 미충족·실패 각 경우의 중단 위치와 남길 증거를 명시한다. 시험 데이터 복구가 필요하면 허용된 범위를 정의하고 최초 결과를 보존한 뒤 수행한다. 임의 삭제나 재편집으로 다음 단계 조건을 만들지 않는다. |

## 작성과 검토에 적용
Precondition의 `[사전 조건]`·`[테스트 스텝]`·`[판정 기준]`과 Script를 대조한다. review.md에 `사람용 구획/항목 → Script 단계 → 근거/보완 이유 → 충족/보완 필요` 대응을 기록한다. 조건·순서·분기·판정 수치와 적용 범위가 같아야 하며 서로 다른 구체화 수준을 의미 변경으로 혼동하지 않는다. 원문부터 빠진 내용도 근거 탐색·보완 대상이다. 양쪽에 복사했다는 사실만으로 근거가 생기지 않는다.
1. 작성자가 위 기준으로 한 번 점검하고 해결 가능한 입력·관찰·분기를 직접 보완한다. 모든 항목을 사용자 질문으로 넘기거나 매번 독립 Agent를 추가하지 않는다.
2. review.md에 적용되는 항목별 `충족 / 보완 필요 / 해당 없음`, 관련 단계, 근거 또는 부족한 내용을 기록한다. '해당 없음'은 실제 시험 범위를 기준으로 한다. 대량 작업에서는 TC별 점검 여부를 남기되 공통 통과 규칙은 한 번 요약하고 개별 문제·분기·결정만 상세히 기록하여 반복 출력을 줄인다. 코드로 자동 판정한 것처럼 쓰지 않는다.
3. 미해결 사항은 제품 기준 결정 필요, 실행 시 입력 연결, 자료/도구 접근 제한으로 구분한다. 명시적인 연결 방법이 있는 실행 입력은 실제 계정/URL 값이 아직 없다는 이유만으로 작성 blocker로 만들지 않는다. 중요한 분기나 기대 결과 자체가 정의되지 않았으면 실행 준비 완료로 표시하지 않는다.
4. 사용자 결정으로 확정된 제품 기준은 decisions와 출처를 유지한다. 해결된 질문과 사용자가 비워 두기로 한 비필수 정보는 blockers에 남겨 다시 차단하지 않는다. blockers에는 현재 결과의 작성/판정/반영을 실제로 막는 미해결 사항만 둔다. 기준의 제품 적용 범위가 바뀌었을 때만 재확인한다.
5. 원격 재조회 일치는 저장 내용 일치다. `verified` 파일명만으로 이 의미 검토를 통과했다고 판단하지 않는다. TC 원문·초안·검토 결과·원격 확인본의 상태를 구분한다.

## 원문에서 찾아 보완할 실행 공백

review.md의 TC별 기록은 최소 `TC 키 | 점검 항목 | 관련 단계 | 진입 상태 → 조작 → 도착 상태 | 충족/보완 필요/해당 없음 | 수정 또는 근거`를 갖춘다. 단순 시험은 간단히 기록하되 'Script 있음', '원문 보존'만으로 충족 처리하지 않는다. 선행 단계의 도착 상태와 다음 단계의 진입 상태가 다르면 준비·복구·분기를 작성하고 실패한 최초 결과는 보존한다.

- **장애·복구**: Backup 디스크를 장애로 만든 다음 Main만 장애인 시험을 하려면 Backup 정상 복구 확인을 연결한다. Failback 다음에 Failover 상태 시험이 오면 재진입 절차 또는 독립 시나리오 초기화를 명시한다. 새로운 제품 기대 동작을 임의로 만들지 말고 원래 시나리오에 필요한 상태를 마련한다.
- **입력 오류**: 잘못된 인증 입력으로 진행이 막히면 다음 화면의 오류 시험으로 바로 넘어갈 수 없다. 유효한 실행 입력으로 진입하는 준비 단계 또는 분리된 분기를 정의한다. 실제 비밀번호·토큰은 TC에 넣지 않는다.
- **값 비교**: IP·서버·설정 값 비교는 대상 별칭과 비교할 기준값의 확보 방법을 Test Data에 연결한다. '원문 사전 조건 없음'은 탐색·보완 완료가 아니다.
- **성능·장시간 관찰**: 각 지표의 시작/종료 사건, 기준 실행과 비교 식, 관찰 대상·기간·증거 수집 방법을 구분한다. 실행 정책의 기록 주기·대기 한도를 제품 합격 임계값으로 바꾸지 않는다. 합격 기준이 관찰 수단으로 판정 가능한지 확인한다.
- **환경별 복제**: 원문이 같아도 단일 서버/클러스터링의 노드 역할·장애 대상·초기 상태가 명확한지 따로 읽는다. 같은 Jira 근거를 재사용할 수 있으나 환경 차이가 없는지를 제목 일치만으로 승인하지 않는다.

문서 접근 제한·제품 기대 동작 충돌은 남길 수 있다. Agent가 해결할 수 있는 시험 순서와 실행 입력 연결을 모두 사람 질문으로 넘기거나 원문에도 있던 공백이라는 이유로 통과시키지 않는다.

## 구성 값 예시 — 제품 요구사항이 아닌 시험 데이터 선택 예시

실제 실행 전에 사용 가능한 채널을 CH1~CH4에 매핑하고, 별개 채널인지 확인한다. 아래 타일 수/구성은 설명용이며 모든 TC에 강제하지 않는다. 실제 원문의 범위와 환경에 맞는 값으로 확정·기록한다.

| 참조 | 구성 |
|---|---|
| L0 | 타일 1=CH1, 타일 2=CH2 |
| A1 | 타일 1=CH3, 타일 2=CH2 |
| B1 | 타일 1=CH1, 타일 2=CH4 |

- A 저장 전에 B 화면 기록 시작 → A 저장 → B1 유지 여부 관찰.
- B1이 유지되고 저장할 수 있으면 B 저장. 사라졌거나 다른 내용이면 증거를 보존하고 B 저장 구간을 중단한다. B1 소실 자체의 합격/실패는 실제 제품 기준이 있어야 판정한다.
- 마지막 저장 우선이 해당 TC의 확정 기준인 경우에만, B1 저장 성공 후 모든 대상 화면을 각각 B1과 비교한다. 단순히 화면끼리 일치하는 것만으로 성공 처리하지 않는다.
- 실시간 반영 관찰과 재접속 후 복구 확인 결과는 분리한다.
