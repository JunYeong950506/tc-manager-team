# TC 양식

| Zephyr 항목 | 작성 원칙 |
|---|---|
| Name | 기능과 상황·검증 목적이 드러나는 제목. 기존 원문의 목적을 보존한다. 복제 식별자는 사용자 요청에 따른다. |
| Objective | 사람이 읽고 어떤 시나리오인지 이해할 수 있는 1~3문장. 주된 검증 목적과 부가 관찰을 구분해 검색·계획에 활용한다. 동시 편집과 실제 동시 저장처럼 서로 다른 시험 범위를 혼용하지 않는다. |
| Precondition | 사람이 직접 수행할 전체 시나리오. `[사전 조건]`·`[테스트 스텝]`·`[판정 기준]`을 순서대로 작성한다. 기존 구성을 유지하며 부족한 조건·절차·기준은 근거를 탐색해 보완한다. 필드명이 Precondition이라는 이유로 스텝·판정 기준을 삭제하지 않는다. |
| Test Script / Step | 실행 입력 확인 → 구체적인 조작 → 관찰·증거 확보 → 다음 단계 진입 조건. 선행 결과에 따라 후속 동작이 달라지면 분기·중단·종료를 명시한다. UI 명칭을 사용하며 확인하지 않은 selector/AutomationId는 만들지 않는다. |
| Test Script / Test Data | 해당 단계의 입력값·데이터 조건·계정 별칭·자원 참조. 비밀번호·토큰과 Pass/Fail 기준을 넣지 않는다. 불필요하면 빈 문자열. |
| Test Script / Expected Result | 관찰 대상의 기대 상태와 비교 방법. 수치·시간 한계는 출처가 있을 때만 사용한다. 실패와 증거 부족을 구분한다. |

## 사람용 시나리오와 실행용 Script

Objective는 시험 목적·상황·범위를 설명한다. Precondition은 아래처럼 사람이 수동으로도 시험할 수 있는 내용으로 작성하고 DB 검색·분류에도 활용한다. Test Script는 **동일한 시험**을 Agent가 수행하도록 구체화한 표현이다. 두 곳에 절차와 판정 기준이 있다는 이유로 한쪽을 제거하지 않는다.

```text
[사전 조건]
1. 필요한 제품·허용/제외 환경·권한·시험 데이터·초기 상태.

[테스트 스텝]
1. 사람이 이해할 대상·조작·관찰 순서.
2. 필요한 분기·중단·복구·종료 절차.

[판정 기준]
1. 관련 스텝에서 확인할 기대 상태와 판정 방법.
2. 근거가 있는 경우 적용 범위와 수치·시간 기준.
```

위 문구는 구성 설명이며 그대로 TC에 붙여 넣지 않는다. 각 구획은 실제 해당 시나리오로 채운다. 별도 사전조건이 없으면 확인한 범위에서 그 사실을 쓰며 무관한 조건을 추가하지 않는다. 계정·장비의 실제 값은 실행 입력에 연결할 수 있고 비밀번호·토큰은 쓰지 않는다. 필요한 입력·분기·관찰 방법은 사람이 수행할 수 있을 만큼 Precondition에도 설명하고, Agent용 참조·증거 수집 세부사항은 Script에서 구체화한다.

구역 제목은 독립된 줄, 번호·글머리표 항목은 각각 별도 줄에 쓴다. 구역 사이에는 빈 줄을 둔다. 화면 폭에 따른 자동 줄바꿈은 항목 구분이 아니다. `[사전 조건] 1. ... 2. ... [테스트 스텝] ...`처럼 한 문단으로 이어 쓰지 않는다. Objective도 여러 문단이면 실제 개행으로 구분한다.

## 오래된 TC의 부족한 내용 보완

- 원문 보존은 불완전한 형식까지 그대로 복사하라는 뜻이 아니다. 구획이나 합격 기준이 없는 과거 TC도 원문 목적·조건·행동·기준을 먼저 추출하고, 빠진 항목을 Jira·Confluence에서 실제 탐색한다. 원문에 내용이 있는 구획을 불필요하게 다시 작성하지 않는다.
- 연결 티켓·요구사항·관련 문서에서 제품/버전/환경이 맞는 근거를 찾고 실제 읽은 발췌와 위치를 evidence.json에, 조회 결과·접근 제한을 search-log.json에 남긴다. 기존 자료가 충돌하면 어느 쪽도 조용히 덮어쓰지 않는다.
- 원문 기준, 문서로 보완한 제품 기준, Agent가 제안한 실행 방법을 decisions/review.md에서 구분한다. 기존 기준은 출처 미발견만으로 삭제하지 않는다. 원래 없던 수치·허용 오차·제품 동작을 추측해 채우거나 사례의 수치를 다른 TC에 적용하지 않는다.
- 탐색 후에도 판정에 필요한 제품 기준이 없거나 충돌하면 관련 구획과 Script에 무엇이 미정인지 사람이 알 수 있게 표시하고 blockers에 이유를 남겨 최종 확인받는다. 관찰 방법·실행 입력 연결처럼 스스로 설계할 수 있는 사항까지 사람에게 떠넘기지 않는다. 자료 접근 실패는 기준 부재와 구분한다.
- 작성·수정 후 Precondition의 각 조건·스텝·판정 기준과 Test Script의 대응을 review.md에 기록한다. 일대일 행 수는 요구하지 않지만 누락·순서/분기 변화·수치/적용 범위 차이를 확인한다. 보완·피드백은 양쪽에 일관되게 반영한다. 사람이 이어받아도 같은 시험과 판정이 되어야 한다.

예: UI 표시 지연을 확인할 때 최종 스크린샷 하나로 판정하지 않는다. 표시 전후 연속 화면 관찰/녹화를 Step에 제안한다. 원문에 없는 ms 임계치를 추가하지 않고, 관찰 정밀도가 부족하면 지연 없음으로 합격 처리하지 않는다. 제안한 시험 방법은 decisions에 기록한다.

사전조건을 만족하지 못한 경우 조건 미충족으로 남긴다. 실행 시 선택 가능한 입력·측정 방법은 Agent가 제안한다. 제품의 기대 동작을 바꾸는 결정과 출처 충돌만 실제 탐색 후 사람에게 묻는다. 출처·작성 방식·미정은 관리 파일에 두며 Zephyr 본문에 JSON/Agent 내부 작업 상태를 넣지 않는다.

효과명·UI 용어만 보고 구체적인 색·모양·렌더링 구현을 추측하지 않는다. 원문의 시각 효과와 주변 화면 구분 요구를 특정한 밝기 변화로 치환하려면 실제 사양 근거가 필요하다. 측정 해상도나 녹화 FPS를 제안하더라도 합격을 보장하는 수치로 만들지 않는다. 짧은 현상이 관측되지 않았다는 사실과 존재하지 않는다는 판정은 구분한다.

Test Script와 거기서 명시적으로 참조한 실행 입력만으로 준비·실행·판정·종료가 연결되게 작성한다. 필요한 모든 환경 값을 TC에 고정하거나 비밀번호를 복사하는 뜻은 아니다. 계정·클라이언트·대상 별칭은 실행 시작 시 실제 자원에 연결하고 선택한 입력을 기록한다. 실행 지침은 `execution-readiness.md`로 점검한다. 새로운 Zephyr 열을 추가하지 않고 기존 3열 안에 필요한 내용을 둔다.


## HTML 원문과 초안의 경계

초안의 title/objective/precondition 및 step/test_data/expected_result는 평문이며 줄바꿈은 실제 개행으로 작성한다. Zephyr에서 읽은 HTML은 tc_source.py로 별도 작업본을 만든 후 사용한다. `<br>` 태그를 줄바꿈 대신 초안에 복사하지 않는다. 다만 HTML 문자열 자체를 시험하는 데이터는 문자 그대로 보존하며 원문의 `&lt;br&gt;`를 태그로 다시 해석하지 않는다. 원문은 출처로 그대로 보존하고 정규화본을 원응답이라고 표시하지 않는다. 링크·이미지 참조는 작업본에 남지만 첨부의 내용 확인을 대신하지 않는다.

게시 payload는 tc_draft.py의 rich 처리로 한 번만 HTML escape한다. 기존 TC 수정 경로도 같은 인코딩 규칙을 사용한다. 준비한 report와 payload에서 줄바꿈용 `<br>`가 `&lt;br&gt;`로 이중 처리되지 않았는지 검사하고, 문자 그대로 시험할 HTML 입력과 구분한다. 원문 HTML을 자동 추측해서 모든 초안 문자열에서 태그를 제거하지 않는다.

MCP에 평문 초안의 개행만 직접 전달하면 HTML 표시에서 줄이 합쳐질 수 있다. `prepare`가 만든 create.json의 objective/precondition을 요약·평문화하지 않고 그대로 전달한다. 한 개행은 `<br>`, 구역 사이 빈 줄은 `<br><br>`로 보존한다. `plain()`은 내용 비교 전용이며 게시용 문자열로 사용하지 않는다. 재조회 때 내용 일치와 `layout_matches(remote_html, draft_text)`의 줄 구분 일치를 함께 확인한다. 이중 escape나 줄 구분 유실은 등록 완료가 아니다. 실제 Zephyr UI를 확인하지 않았으면 화면 검증 완료라고 보고하지 않는다.
