# tc-manager 1.4.8 — 세 가지 업무

1.4.8 팀 배포본은 Connect-Zephyr.cmd 재실행 시 기존 설정 보존과 별도 MCP 시작 검사 실패를 구분해 안내한다. 시간 초과를 기존 연결 끊김이나 캐시 손상으로 단정하지 않으며, 시작 실패를 연결 완료로 처리하지 않는다. 연결 스크립트 변경은 새 ZIP 내용 적용이 필요하다.

1.4.7 팀 배포본은 기존 ZIP 업데이트를 기본으로 유지하며, Update-TC-Manager.cmd에서 선택적으로 Git 원격 등록·설치/갱신·자동 업데이트 설정을 수행한다. 저장소 주소는 update-source.json으로 관리해 다른 담당자에게 인계할 수 있다.

1.4.6은 티켓당 1개 제한 없이 시나리오 후보를 도출·중복 대조한 뒤 사용자가 복수 선택한 항목을 상세 작성한다. 후보의 근거·재사용 가능성·미확인 조건을 선택 전에 보여준다. 관점 선택과 후보 선택, 본문 최종 검토는 별개다.

1.4.5는 create 시작 시 기본값(기능 검증)·성능·안정성을 복수 선택하고 직접 입력을 추가하는 질문을 제공한다. 선택 범위를 자료 탐색·중복 대조·작성·검토에 적용하고 재개 시 보존한다. 이미 지정한 관점은 다시 묻지 않는다.

1.4.4 팀 배포본은 설치·연결 한글 안내, 전용 npm 캐시, 실패 코드 진단과 선택적 캐시 복구를 포함한다. TC 작성·검토 역할 구조는 바꾸지 않는다.

1.4.3은 `/tc-manager:help` 응답 첫 줄에 현재 호출된 도움말 스킬의 버전을 표시한다. 설치 파일의 최신 버전과 세션에서 호출된 버전을 혼동하지 않는다.

1.4.2는 Precondition의 구역·항목 줄바꿈과 구역 간 빈 줄을 게시 전에 검사하고, HTML payload 및 재조회 검증에서 보존한다. 내용이 같아도 줄 구분이 사라지면 완료로 표시하지 않는다.

1.4.1은 프로젝트를 설치 시 하나로 고정하지 않는다. 팀 기본 사이트의 PX·PXW를 함께 매핑하고, 실제 대상은 사용자 요청·TC/Jira 키·링크에서 결정한다. 모호한 범위만 질문하며 DB와 원격 반영은 프로젝트별로 구분한다.

| 업무 | 명령 | 예시 |
|---|---|---|
| 기존 TC 정리·DB화 | `/tc-manager:convert` | 첨부 XML의 TC를 새 양식으로 정리하고 DB에 저장해줘. |
| 신규 TC 작성 | `/tc-manager:create` | 이 Jira 변경 티켓에 필요한 TC를 작성하고 기존 TC와 대조해줘. |
| 테스트 준비 | `/tc-manager:plan` | 이벤트 패널 회귀 테스트를 준비해줘. |
| 사용법 | `/tc-manager:help` | 세 업무와 필요한 입력 안내 |

이 프로젝트에서는 `/tc-manager 기존 TC 정리해줘 ...`처럼 자연어로 요청해도 됩니다. 내부 manage가 세 업무 중 하나로 연결하며 자동완성 업무 목록에는 숨깁니다. 단건/여러 건·수정·재개는 별도 명령이 필요 없습니다.

## 공통 흐름
Jira·Confluence 근거 탐색 → 기존 TC DB 검색·대조 → 작성/선정·자체 점검 → 사람이 최종 결과 검토 → 승인 범위의 Zephyr 반영·재조회 → DB 확인본 저장.
별도 Agent는 매번 호출하지 않습니다. 요청받거나 중요한 기준 충돌을 확인할 때만 독립 검토를 추가합니다. 자체 점검은 독립 검토로 표시하지 않습니다.

1.3.1에서는 Precondition에 `[사전 조건]`·`[테스트 스텝]`·`[판정 기준]`의 사람용 전체 시나리오를 유지합니다. 오래된 TC에 없는 조건·절차·기준은 Jira·Confluence에서 탐색해 보완하고, Test Script와의 대응을 검토합니다. DB에서는 구획별 의미를 구분합니다. Objective·Precondition은 사람이 이해하고 검색할 수 있는 내용이며 Test Script는 Step/Test Data/Expected Result입니다. 기존 TC 제목·목적·제품 합격 기준을 보존합니다. 테스트 준비는 기본적으로 원본 TC를 유지하는 Test Cycle 구성을 제안하고, 명시적인 분류 변경은 폴더 이동으로 구분합니다.

Test Script는 명시된 실행 입력만으로 준비 확인·조작·분기·관찰·판정·종료가 연결되게 작성합니다. [실행 준비 점검](references/execution-readiness.md)에서 최초 실패와 복구 결과, UI 차단과 실제 요청 거부, 동시 편집과 동시 저장을 구분합니다. 원격 재조회 일치만으로 TC 품질까지 통과했다고 표시하지 않습니다.

## 설치와 팀 배포
이 폴더 또는 `tc-manager-1.4.0.zip`을 Claude Code 플러그인으로 배포합니다. Python 3.10+가 필요합니다. 이 저장소에서는 다음으로 업데이트합니다.
```text
claude plugin update tc-manager@sqma-local --scope local
```
새 Claude Code 세션에서 명령을 확인합니다. 플러그인 스킬은 `tc-manager:convert/create/plan/help`입니다. 설치 scope는 프로젝트 로컬이며 다른 프로젝트/팀원에게 자동 설치되지 않습니다.

콜론 없는 단축키가 필요하면 `references/short-command/SKILL.md`를 대상 프로젝트의 `.claude/skills/tc-manager/SKILL.md`로 복사합니다. 기존 파일이 있으면 내용을 검토하고 백업 후 교체합니다. 플러그인 자체와 단축키는 별개입니다.

각 팀원은 자기 계정의 Jira·Confluence·Zephyr 연결을 사용합니다. API 토큰은 현재 MCP 환경 설정에서 읽습니다. 이 플러그인이 OAuth 설정을 복구하거나 토큰을 패키지에 넣지 않습니다.
- `.tc-manager/target.json`: 실제 조회한 사이트·프로젝트·폴더 기본값.
- `.tc-manager/library.json`: 기존 registry DB 경로와 사이트/프로젝트별 namespace 매핑. `examples/library.json` 참고.
- 상대 DB 경로는 프로젝트 기준이므로 개인 PC 절대 경로가 필요 없습니다.
- 실제 설정·DB·인증·업무 자료는 배포하지 않습니다. 각 PC의 DB는 자동 공유되지 않으며 공용 서비스 연계는 조직별 연결 도구가 필요합니다.

## 저장소와 재개
기존 registry 스키마와 출처·버전 이력을 유지합니다. DB가 없으면 검색 결과를 unavailable로 표시합니다. 기준 버전 미선택 TC는 여러 버전을 한 TC의 후보로 묶어 반환하며 최신이라고 추정하지 않습니다.
`tc_library.py`는 기존 저장소의 adapter이고 의미 검색 모델이나 자동 동기화 서비스는 아닙니다. 후보의 전체 Script를 Agent가 비교하고 필요한 원격 정보를 재조회합니다.

작업별 workflow.json·review.md·원문/출처·원격 journal을 남깁니다. 신규 등록은 기존 tc_draft.py의 prepare/pending/created/verify/verify-xml 검사를 유지합니다. 수정본은 새 버전으로 저장하며 pending 상태에서 원격 생성을 반복하지 않습니다.

## 구현과 검증 범위
세 업무는 Claude가 도구를 조율하는 Skill 절차입니다. DB 저장·검색·버전 검사와 신규 등록 재조회 비교는 Python 코드가 보조합니다. 기존 TC 수정·Cycle/폴더 생성은 Zephyr MCP 도구로 실행합니다. 기존 Cycle에 TC를 반복 연결할 때는 번들 `tc_cycle.py`를 사용하며 최대 4개 요청씩 처리합니다. 현재 도구/API로 수행할 수 없으면 미반영 상태를 남깁니다.
로컬 테스트와 설치 확인은 실제 Jira/Confluence 탐색·Zephyr 쓰기 성공을 증명하지 않습니다. 제품 테스트 실행기는 포함하지 않습니다.

1.2.0의 plan은 폴더 이름 외에 목적·조건·인접 기능을 대조하고 클라이언트/서버 OS를 구분합니다. TEST_CASE와 TEST_CYCLE 폴더 ID를 구분하며 연결 도구는 검토한 계획 해시·중복·전체 페이지·Not Executed 상태를 검사합니다. 개인 TC 키나 Cycle ID는 작업 파일에만 두고 배포본에 넣지 않습니다. [테스트 준비 절차](references/test-preparation.md)를 참고하세요.

API 토큰 방식 MCP의 필드 병합, 생성 folderId와 이동 folder의 차이, 빈 단계 처리, APPEND/OVERWRITE 최종 선택은 [현재 도구 계약](references/zephyr-mcp-contract.md)을 따릅니다. 기본 도구의 성공과 세 업무 전체 흐름의 성공은 구분합니다.

## 기존 코드 재사용
scripts/tc_registry.py와 scripts/qa_manage.py는 이전 플러그인에서 변경 없이 가져온 호환 코드입니다. scripts/build_test_manager.py가 원본과 같음을 검사한 뒤 배포합니다. 관리 상태와 품질 판단을 이 스키마의 draft 라벨 하나로 해석하지 않습니다.

## 1.4.0 — 내용 검토와 약식 수행 연결

- 기존 세 명령을 유지하며 `이 TC의 약식 수행을 준비해줘`, `이 약식 수행 결과를 반영해줘`로 이어서 요청합니다.
- 내용 검토 6개 항목과 미해결 내용을 TC 버전·본문 해시에 연결해 저장합니다. 새 버전에 과거 검토 결과를 자동 적용하지 않습니다.
- 약식 수행의 단계·환경·관찰 방법·한도·제외 범위를 전달 파일로 준비합니다. 요청 저장만으로 실제 실행을 시작하지 않습니다.
- 실행 피드백은 TC 결함 / 환경 부족 / 도구 한계 / 제품 결함 / 요구사항 충돌로 나누고 해당 조치로 연결합니다.
- 약식 확인과 정식 수행·제품 Pass/Fail·사람 승인·Zephyr 반영을 구분합니다. 기존 TC 본문은 자동 변경하지 않습니다.
- `tc_readiness.py`와 공용 서비스의 `readiness.get/record`가 같은 저장 규격을 사용합니다. 스킬 배포 ZIP에 웹 서버/대시보드는 포함되지 않습니다.

[절차와 전달 규격](references/readiness-workflow.md)을 참고하세요. 실제 실행 Agent 자동 기동/결과 수집기는 이번 관리 플러그인에 포함되지 않습니다.


## 1.3.1 보완

- 짧은 요청의 명시된 하위 범위를 유지하고 전체 작업을 내부적으로 분할·재개합니다.
- 단계별 시작/종료 상태, 장애 복구·입력 오류 분기, 측정·관찰 방법을 검토 기록에 남깁니다.
- Jira와 Confluence의 실제 탐색 여부와 접근 제한을 구분합니다. 이슈 상태만으로 기준 미정이라고 단정하지 않습니다.
- Zephyr HTML 원문은 새 평문 작업본으로 변환하며 원문·링크·이미지 참조를 보존합니다.
- 공통 자료 묶음에서 해당 TC가 인용한 출처만 DB에 저장하며 단계별 출처 지정도 지원합니다.
- 형식 검사·DB 저장과 내용 품질을 구분하고 복제본을 포함한 실제 TC 수를 집계합니다.

이 업데이트는 기존 DB의 초안이나 Zephyr TC를 자동으로 재작성하지 않습니다. 새 세션에서 수정할 대상을 지정해 재개하세요.
